# Pairing a phone with your laptop

Everything it takes to control a laptop's terminals from a phone, in the order
you meet it: stand up a server, build a Host that is allowed to reach it, enroll
the laptop, scan its code with the phone, approve the pairing, connect.

The screens below are the real components, rendered from the same stories
Chromatic watches. They are static — nothing here is wired to a live server.
One of them carries `autoplay` because a docs page does not run a story's `play`
by default, and its state — a painted terminal — only exists after it runs.

> **This is a walkthrough, not a spec.** It lives outside `docs/specs/`, so the
> fold discipline in `AGENTS.md` does not apply to it and `spec-lint` does not
> check it. Where it disagrees with a spec, the spec is right. The three it
> leans on are `server.md` (what the server and the installer do),
> `remote-security-model.md` (why the ceremony has the shape it has), and
> `pocket-app.md` (the phone).

---

## 0. Three parties, five layers

| Term | Who that is here |
| --- | --- |
| **Client** (Dormouse Pocket) | the phone. Holds a passkey and one X25519 key per paired Host. |
| **Host** (Dormouse Terminal) | the laptop being controlled. Holds the ACL. **Final authority for access decisions.** |
| **Server** | the coordinating service: accounts, passkey registration, challenges, and relay. *Not* the authority for Host access, and it reads none of what it relays. |

Access is deliberately split across five layers, and a connection needs all of
them to agree:

| Layer | Responsibility |
| --- | --- |
| Noise channel | Confidentiality, and both endpoints' long-term keys |
| Passkey | Fresh user presence, *inside* that channel |
| Client static | Long-lived client identity, one X25519 key per Host |
| Host ACL | Authorization |
| Host | Final access decision |

Two consequences shape every screen after this one. **Adding a passkey to your
account does not grant a new phone access to any machine** — passkeys sync,
authorization does not, so each browser must be approved on each laptop, in
person, once. And **the server is a ciphertext pipe**: it never learns a pairing
decision, a machine's name, a keystroke, or a notification's text, so nothing
below asks you to trust it with any of them.

## 1. Stand up the server

The whole self-host story today is one coordinating server on your own laptop,
reachable only from your tailnet. One idempotent command builds the current
checkout into a self-contained release and installs it:

```sh
./deploy/local/install-macos.sh        # macOS
.\deploy\local\install-windows.ps1     # Windows
./deploy/local/install-linux.sh        # Linux
```

The Linux one is the always-on shape: run it with `--linger` on a spare tailnet
machine and the relay outlives your logout, which is what lets you reach a Host
that is not the laptop you are sitting at.

Each installs under your user profile, needs no administrator rights, and wires
up a per-login service plus Tailscale Serve:

```text
LaunchAgent (RunAtLoad + KeepAlive)
  — a Windows Scheduled Task at logon, or a systemd user unit —
        |
        v
Dormouse Node server on 127.0.0.1:3100
        |
        v
tailscale serve --bg terminates private HTTPS
        |
        v
https://<laptop>.<tailnet>.ts.net
```

Then check it and read the generated password out in your own terminal:

```sh
"$HOME/Library/Application Support/Dormouse Server/bin/manage" verify
"$HOME/Library/Application Support/Dormouse Server/bin/manage" show-password
```

Two things to carry forward:

- **That origin is durable WebAuthn identity.** The passkey you are about to
  create is bound to `https://<laptop>.<tailnet>.ts.net` byte for byte.
  Renaming or re-enrolling the Tailscale node means redoing the passkey and
  every Host enrollment — which is why the installer stops rather than rewrite
  a changed origin for you.
- **HTTPS is not optional.** WebAuthn needs a secure context and only
  `localhost` is exempt, so a real phone needs the TLS origin. For a
  desktop-only dev loop, generate a 32-byte setup credential and run
  `DORMOUSE_SETUP_PASSWORD="$(openssl rand -hex 32)" pnpm dev:pocket-server`
  on `localhost:3000` is the shortcut.

The setup password gates exactly one thing: enrolling a Host from somewhere
else. It never leaves your machine except to that endpoint — and on a happy path
you never read it out at all: a Host on *this* laptop enrolls from the one-time
offer the installer leaves it (section 3), and the phone sets itself up from a
scanned code (section 4), which is the *only* way any browser can register a
passkey. `show-password` is the enrollment fallback.

## 2. Build a Host that is allowed to reach it

Shipped Dormouse builds bake in a relay allowlist of
`https://*.dormouse.sh wss://*.dormouse.sh` and nothing else, enforced inside
the Node process that holds the relay socket rather than by any webview CSP. A
self-host origin needs a local build that widens it:

```sh
DORMOUSE_REMOTE_CONNECT_SRC='https://*.ts.net wss://*.ts.net' pnpm dogfood:standalone
DORMOUSE_REMOTE_CONNECT_SRC='https://*.ts.net wss://*.ts.net' pnpm dogfood:vscode
```

Skipping this has a specific, recognizable symptom, and you will see it in the
next section rather than as a mysterious failure: enrollment is refused
locally, before any credential leaves the machine.

## 3. Enroll the laptop

**Settings → Remote control**, at the bottom of the app-global Settings dialog
(the sliders icon at the far right of the baseboard). Because the server from
section 1 is installed on this very laptop, there is nothing to type:

<Canvas of={RemoteControl.OfferAvailable} />

The installer left a `run/enroll-offer.json` next to its state — this install's
origin plus a one-time token the server redeems in place of the setup password
— and the Host reads that same file from the well-known path for the platform.
It lasts for 24 hours or until the first Host enrolls, whichever comes first.
Press **Enroll** and the machine is connected.

The one thing the card is careful about: **the token never reaches the webview.**
The status the card renders from carries the origin and nothing else; pressing
Enroll sends the name and an echo of that origin, and the Host service re-reads
the file itself. That re-read is also why a card left on screen for an hour is
safe to press: redeeming an offer unlinks it, so a spent one fails with a
message saying so rather than half-enrolling. The echo covers the other half of
the same hour — if the installer ran again and rewrote the offer, the origin on
disk no longer matches the one you read, and the service refuses rather than
spend a one-time token on a server you were never shown.

### The typed form, for a server somewhere else

"Enroll with a different server…" unfolds the original three-field form, which
is also what you get on a laptop with no local install — a second machine
enrolling against the first one's server, or an offer already redeemed.

<Canvas of={RemoteControl.Unenrolled} />

This is UI rather than a console incantation because it is the one step a
self-hoster cannot skip. Three rules it exists to honor:

- **The password is passed through, never held.** It goes straight to the Host
  service — the party that actually talks to the server — and is cleared on
  success only. A failed enroll is usually a typo in one of the other fields,
  and wiping the password would make every retry a fresh trip to the password
  manager.
- **Refusals are shown, not swallowed**, in the same words the card uses:

<Canvas of={RemoteControl.EnrollRefused} />

  The build refuses the origin before the password is sent anywhere. Saying so
  in those words is what keeps it from reading as a wrong password.

- **The bearer token never comes back.** Enrollment answers
  `{ hostId, serverUrl }`; the `hostToken` stays in the Host service and on
  disk, and never enters the webview.

On success the section flips to the enrolled view. Note the last line —
enrolling connects the machine to a server; it pairs it with nothing.

<Canvas of={RemoteControl.ConnectedNoDevices} />

### Show the phone a code

An enrolled machine can mint one, on request:

<Canvas of={RemoteControl.SetupPhoneQr} />

That code is the origin you would otherwise type into mobile Safari, carrying a
**setup token** the server issues and will redeem in place of the setup
password, plus an **invitation**: an id and a one-use public key that are the
*laptop's own* and never go near the server. The invitation's private half stays
in the laptop's Host process, so a phone that completes a handshake against it
has provably read this screen — which is what makes it worth something in §6.
(`docs/specs/server.md` → Setup tokens and the pairing QR owns the grammar.)

Neither lives long: five minutes, one use. The code is shown on request rather
than left standing on screen, and the panel says so the moment a phone completes
a handshake against the invitation rather than going on offering a code that can
no longer work — the laptop knows that itself, because the key it was completed
against is the laptop's own.

The panel keeps listening past that, because it is the thing the pairing modal
in §6 is covering: once the request has been answered it stops pointing at a
phone that has already finished, and — where a person answered it — says which
way it went (§6). This is the frame a socket that dropped mid-ceremony leaves,
where nobody decided anything:

<Canvas of={RemoteControl.SetupPhoneFinished} />

## 4. Scan it with the phone

Open the server origin on the phone. A browser that has never been here has
exactly one thing it can do, and the screen leads with it:

<Canvas of={SetupOrSignin.FirstRun} />

**On iOS, install to the Home Screen before you do any of this** — the installed
app is a separate storage partition from the Safari tab, so anything set up in
the tab has to be set up again from scratch. Pocket says so on this screen,
above the action rather than after it:

<Canvas of={SetupOrSignin.FirstRunNeedsInstall} />

**Scan a setup code** opens a rear-camera scanner inside Pocket. It reads the code
as *data* — nothing navigates, and the text goes straight to the one parser that
decides whether it is a setup code for this server — with a paste field beside
it, because a desktop browser and the localhost dev loop have no camera:

<Canvas of={ScanInvitation.Scanning} />

Pointing the phone's *own camera* at the laptop instead is a different thing,
and Pocket treats it as one. Following that link reaches the right origin and
nothing else: the fragment is erased before the first render, nothing from it is
kept, and the code is not spent. On iOS the camera opens Safari, which is not
where the installed app's keys live, so the only useful thing left to say is
where to scan:

<Canvas of={SetupOrSignin.ArrivedByCamera} />

There is no setup password anywhere in this flow, and no typed credential: the
code on the laptop's screen *is* the credential. A phone that already holds a
passkey signs in instead and scans only to add a machine:

<Canvas of={SetupOrSignin.Welcome} />

Either way, that one action creates the account's first passkey (or signs in
with a synced one) and moves straight into pairing. Three things happen that you
cannot see:

- A **per-Host key** is minted — a non-extractable X25519 keypair, held in
  memory until the laptop approves and only then written to IndexedDB. This
  browser can agree with it and can never export it. It is this browser's
  identity *for this laptop*; a different laptop gets a different key.
- **The code is spent either way.** A phone with no passkey redeems it to
  register one; a phone that already has one retires it at
  `POST /api/setup/retire`, so a photograph of the laptop's screen cannot
  register a passkey afterwards. A refusal stops the run — a dead code is one
  the laptop would refuse too.
- The session token that lets the phone open a relay socket is issued. Presence
  itself is proved again inside the pairing channel, over a challenge derived
  from that handshake, so signing in buys routing rather than authorization.

A browser that cannot do X25519 at all never gets here: Pocket probes for it
before any of the above and shows a fixed upgrade requirement instead. Runtimes
are gated, not degraded.

## 5. Coming back

This screen is not on a first run's path. A phone that has just scanned goes
scan → two digits → terminal, and never sees a list; it is where a phone lands
on every session *after* the first, and where an interrupted one falls back to.
Read it now for what a paired phone looks like from the outside, then carry on
to §6 for what happens on the first run instead.

<Canvas of={HostsView.MixedList} />

One row per machine **this phone holds a key for** — a Host enrolled on the
server but never paired with this browser is not a row at all. The label comes
from the record, which learned it inside an encrypted pairing outcome; only the
online dot comes from the server. The card above them is push, which §7 comes
back to.

Each row offers exactly one action, and nothing is asked to decide which.
**Connect** is offered where this browser holds an authorized record, and
**Pair again** where an authenticated denial took that authorization away —
which is the only thing that can move a row, and which keeps the pinned Host key
while dropping the authorization. **Remove** forgets the machine locally, and
queues the deletion of its push mapping first, because the id in the record is
the only handle that can name that row again.

## 6. The pairing ceremony

Pairing runs end to end between the phone and the laptop, through a server that
routes ciphertext and reads none of it:

```text
phone                        server                        host (laptop)
  |-- e2e init (Noise msg 1) -->|-- e2e init {clientId} ------>|  against the key
  |<-- e2e response ------------|<-- e2e response ------------ |  the QR carried
  |-- reauth begin/finish ----->|  challenge bound to this     |
  |                             |  handshake, and no other     |
  |-- e2e transport ----------->|-- e2e transport ------------>|  proof verified,
  |    {code, label, proof}     |                              |  modal opens
  |<-- outcome (encrypted) -----|<-- outcome -----------------|  ACL record saved
```

The handshake runs against the one-use key printed in the QR, which never left
the laptop, so a phone that completes it has provably read *this* screen. The
server sees two routing ids and a handshake hash.

Then the phone shows two digits, and the laptop asks for them. The phone paints
them the moment they exist, before it knows how any of this ends:

<Canvas of={PairingCode.Waiting} />

<Canvas of={Pairing.Default} />

The direction is the whole trick. A relayed or injected request has no screen
to read from, so authorizing requires holding the device that is asking — and
the laptop compares the digits itself, exactly once
(`docs/specs/remote-security-model.md` → Pairing owns the rule and what it rules
out). The modal is the whole security model in one screen, which is why it is a
modal and not a settings row.

Exactly once is unforgiving, so the panel behind the modal says which way it
went. Mistype the digits and the code is spent — there is no second try, and
the paired count above is absolute, so nothing else on that screen would have
moved:

<Canvas of={RemoteControl.PairingOutcomeCodeMismatch} />

- **Local confirmation is the only path into the ACL.** Not signing in, not
  owning the account, not holding a synced passkey. Someone with your account
  and your passkey still gets no further than this dialog on a machine they are
  not standing at.
- **It has to not read as a formality.** Hence *"Only authorize if your phone is
  showing a two-digit code. If it shows an error or no code, cancel this
  request."* — the copy names the failure mode, because a request that shows no
  code is exactly what an injected one looks like.
- **The label is the only thing the phone chose**, and it is bounded and
  stripped before it is drawn. Everything else about the Client — its key, its
  passkey — was already proved by the handshake and the assertion, so there is
  nothing left for a human to squint at.
- **"Adds it to this machine only"** is doing real work. The ACL is per-Host
  and local; your other laptops are unaffected and will each ask separately.

Confirming writes one `HostAclRecord` binding *that passkey credential* to *that
Client key* — a pair, not either one alone — and is bound to the ceremony's
immutable `pairingId`, so a request that changed underneath a displayed modal is
rejected rather than silently authorizing a device nobody was shown.

Two cases the copy has to survive: a phone that suggested no label, and one long
enough to wrap.

## 7. Connect

Pairing is once. Connecting is every session, and it re-proves everything:

```text
phone                        server                        host
  |-- e2e init (Noise msg 1) -->|-- e2e init {clientId} ------>|  against the key
  |<-- e2e response ------------|<-- msg 2 = 32-byte challenge |  the phone pinned
  |   ONE biometric prompt,     |                              |
  |   over a challenge derived  |                              |
  |   from this handshake       |                              |
  |-- e2e transport (proof) --->|-- e2e transport ------------>|  challenge consumed,
  |<-- outcome (encrypted) -----|<-- outcome -----------------|  proof + ACL checked
  |====== protocol-v1 inside the same Noise session ==========>|
```

A connection succeeds only if the handshake completes against the Host key this
phone pinned at pairing, the passkey proves fresh presence over a challenge
derived from *this* handshake, and one ACL record holds all four of the account,
the passkey credential, that key's hash, and the Client key the handshake
authenticated. The Host decides alone, and its denial says only
`pairing-required` — which half missed is its own business.

One handshake feeds the whole thing, so it costs the user a single Face ID
prompt.

A successful pairing continues straight into all of this, so the approval you
just gave on the laptop lands the phone in a terminal rather than back on the
Hosts list. Later sessions start here instead, at that row's **Connect** — and
if the laptop has forgotten this browser in the meantime (an ACL reset, a
hand-edited record), the denial says so and the row goes back to offering
**Pair again**.

Then the payoff — the same mobile terminal UI, driven by the laptop's real
sessions:

<Canvas of={PocketWall.ConnectedShell} story={{ autoplay: true }} />

Push is asked for back on the Hosts view rather than over the terminal you just
tapped Connect to reach — the card you already saw in §5, above the list from the
moment anything is paired. It is one card and not one per machine because the
permission prompt and the subscription it mints belong to the whole browser: the
tap grants once and registers every paired machine. Afterwards the card collapses
to a line and each paired row says **Push on** for itself:

<Canvas of={HostsView.PushSubscribed} />

The offer appears only where push can work — an installed app on a server with
push configured (§1). A phone in a Safari tab is told to add Dormouse to the Home
Screen instead, which is also where a server with push disabled says so.

A notification is the one message the two ends exchange with no live session
between them, so it gets the same treatment as everything else: the laptop seals
each one to that phone's own key, and the server forwards a sealed envelope it
holds no key for. The service worker on the phone is what opens it — and if
anything about that fails, it shows a content-free "something needs attention"
rather than nothing, because a worker that shows nothing gets the browser's own
"site updated in the background" notice instead.

## 8. Living with it

Back on the laptop, the section now counts what is paired:

<Canvas of={RemoteControl.ConnectedOneDevice} />

The push alarm's settings, directly above that section, carry the proof of the
whole chain you just built: **Send test push**. Nothing about it is simulated —
the test goes through the same Host, the same ACL, and the same server a real
alarm would, so a phone that buzzes is evidence of everything from §1 to §6 at
once. Its answers are kept deliberately distinct, because they call for
different responses: on a machine that has enrolled (§3) but has no phone with
push notifications enabled yet, "nowhere to send it" is the ordinary answer, not
a failure —
while a fan-out that no phone accepted is one worth chasing. The notification
itself is titled to say that nothing actually needs attention, so a test that
lands hours late, or on another paired phone, cannot masquerade as a real
alarm. (The spoken alarm has a sibling **Play test sound**; both live in
`docs/specs/alert.md` → Alarm settings.)

**Displaced** is the one connection state that needs a person. Another Dormouse
instance enrolled with the same `hostId` took the relay slot, and this one stood
down — terminally, on purpose, because two instances fighting over a slot is
worse than one stopping. Reconnect takes it back, and displaces the other in
turn.

<Canvas of={RemoteControl.Displaced} />

**Disconnect** asks first, because forgetting the enrollment drops every paired
phone until each pairs again.

<Canvas of={RemoteControl.ConfirmingDisconnect} />

Four limits worth knowing before they surprise you:

- **Clearing site data destroys the per-Host keys.** That is a re-pair, by
  design: the identity the laptop authorized is gone — and the storage partition
  those keys live in is per-browser, as §4 warns.
- **A scanned code is good for one pairing.** The laptop reserves its invitation
  the moment a phone completes the handshake against it, so a re-pair later
  needs a fresh code; the one a reload loses is simply gone — five minutes was
  its whole life anyway.
- **A code opened by the phone's camera never reaches an installed iOS Pocket.**
  The camera opens Safari, which is the other storage partition (§4), and the
  Home Screen app launches at its own start URL with no hash on it. The recovery
  is to open the installed app and scan the same code from inside it.
- **A dropped WebSocket returns the phone to the Hosts view.** Tap Connect
  again; there is no resume protocol.

## 9. What is not built yet

So nothing above reads as a promise:

- **Revocation is editing a JSON file by hand.** There is no management UI and
  no relay frame carries a revocation. Deleting a *machine* takes effect within
  a minute — the server re-reads the file and drops that machine's socket — but
  withdrawing one *phone's* approval is the laptop's own list, and takes effect
  when that laptop restarts. **Remove** on the phone is not that list: it
  forgets the machine locally, and a phone that pairs again arrives with a new
  per-Host key, which the laptop cannot match to the old record — so it appends
  a second approval and goes on counting both. One phone, "2 paired phones",
  and the first record still live.
- **Approval is Approve/Deny only.** Choosing a standing grant at pairing time
  — observe-only versus interactive — is designed but not built. Every paired
  session today gets full input.
- **The Host does not show you who is connected.** A viewer list with
  per-viewer disconnect is staged.
- **Terminals only.** The shipped protocol carries terminal surfaces and
  nothing else — no browser surfaces, no thumbnails, no scrollback.
