# Hosted account security: rationale

## Origin boundary

Cookie reads (2026-10-11):

- The packed adapter admits `get-session` and `list-accounts` whatever `Origin` they present, and the cookie routes used to admit a read with no `Origin`. Without CORS another page cannot read the answer, but the request still runs: a database lookup, a Better Auth rate-limit count against the visitor's address, and, pre-launch, the deletion of an unlisted user's logins (`prelaunchAuth` runs on every cookie GET, a cookie route's lookup included). The 2026-10-04 and 2026-10-07 audits read "cookie route" both as covering the auth reads and as not, so the rule now names every read.
- The auth reads are gated by default rather than by a list, so a read a later adapter release adds is gated too; only a provider callback (a cross-site navigation, or Apple's form post) and the CSRF challenge (which any page may start from, and which acts on no login) are open.
- Callers, inventoried 2026-10-11: the account page's own fetches (`hosted/src/api.ts`, `credentials: "same-origin"`); the account's cookie routes and pre-launch gate (`cookieAdmin`, `prelaunchAuth`), which call the auth handler in-process and so never meet the rule; and the release smoke (`hosted/scripts/preview-smoke.mjs`), which sends what the page sends. Nothing on the relay or voice origin makes a cookie read: the relay bundle carries no cookie or auth route (`hosted/server/tests/boundary.test.ts`), speak is bearer-only, and the `__Host-` login cookie never reaches a sibling Worker. Pocket, the one-time page, the desktop, and the website make none; the desktop only opens account pages in the system browser.
- No caller needs a sibling's `same-site` or a navigation's `none`, so neither is admitted. Script on the relay origin renders untrusted terminal output (`docs/specs/hosted.rationale.md` -> "Application boundary"), so admitting it would admit the one page the origin split distrusts.
- A missing `Sec-Fetch-Site` is refused rather than trusted: a browser without Fetch Metadata (Chrome before 76, Firefox before 90, Safari before 16.4) sends a same-site image or script request with neither it nor `Origin`, the shape a non-browser caller has. Such a browser cannot load the account page; every caller this deployment has is in-process or can send the header.
- The requests that stay open to other sites (a provider callback, the CSRF challenge) still carry the login cookie, as does the provider list, which strips it before the handler. `prelaunchAuth` therefore looks up every auth read but those two and refuses one the account's own page did not make, so no route reaches its lookup or deletion ungated (dormouse-bot on #1104, 2026-10-11, found `/api/providers` reaching it).
- The lookup is keyed on the open paths, not on a list of reads (dormouse-bot on #1104, 2026-10-11): Better Auth 1.7.7 also serves `list-sessions` and `account-info`, which take a login and the second calls the provider with its token. The packed adapter 404s both today, so a list would hold only until an upgrade. `boundary.test.ts` enumerates the installed Better Auth's GET endpoints.
- Writes stay unlooked-up so the adapter's Origin and CSRF refusals still come before any database read. The one write that starts something with a login is `link-social`, whose callback is open: an unlisted login can attach another identity its holder controls to its own unlisted account (pinned in `workers.test.ts`), which grants nothing, since every read still deletes its logins. Before 2026-10-11, the callback's lookup ended that login first.
- The deletion stays on the read rather than moving to sign-in: the unlisted logins it removes are created inside a provider callback the packed adapter completes, where only its signed session cookie names them. Every use of a login starts with a read, so the gated read is its first use.
- 403, not a signed-out answer, so a refusal never reads as a logout.

## Deployment boundary

pgstencil provenance at deploy time (2026-10-20):

- Renovate opens a pgstencil bump as soon as a release is approved (`.github/renovate.json`), and a production deploy can follow its merge within hours, between two nightly audits. The `verify` job therefore asks npm for each package's registry signature and provenance attestation before every deploy.
- npm verifies the signature, the certificate chain, and the subject against the registry's tarball, not who signed: the payload's workflow claim is the signer's own statement. Reading the certificate's SAN and source-repository digest, and the commit's place on `main` and its audit, means decoding the bundle and calling the GitHub API, so that stays in the nightly audit rather than in a deploy script.
